## Product design

### Goals / Non-goals

Goals (v1):
- Give an MCP-connected agent read and core write access to Jira Cloud issues (search, read, create, update, transition, comment) and Confluence Cloud pages (search, read, create, update), plus the project/space listings needed to address them.
- Credentials (Atlassian site URL, account email, API token) travel only in per-request MCP Headers, are never persisted by the service, and are scoped to the single request that carried them (no cross-tenant leakage when one container serves multiple tenants concurrently).
- Every call is auditable: structured logs correlate a request id to which tool ran and which Atlassian endpoint it hit, without logging the credential values or full issue/page bodies.

Non-goals (v1 — explicitly out of scope, candidates for a follow-up ticket):
- OAuth 2.0 (3LO) authorization-code flow (consent screen, token exchange, refresh-token storage). The service is stateless and serves many tenants per container; building and persisting an OAuth token store is a different shape of service and is a platform/gateway concern (see Option analysis).
- File attachments (upload/download) on Jira issues or Confluence pages — binary handling adds a second content type and size-limit story not needed for the core "read/write tickets and docs" ask.
- Jira Software agile objects (boards, sprints, backlogs) — a separate Agile REST API, not requested by the ticket.
- Confluence/Jira webhooks or any push/event surface — the service is a stateless pull-only MCP tool server, consistent with every other vendor MCP in this org.
- Bulk/batch operations (bulk create, bulk transition) — single-resource operations only, consistent with the "explicit id, no fuzzy batch" rule for write tools.
- User/group administration (inviting users, managing permissions) — out of scope; this is a content-access connector, not an Atlassian admin console.

### Acceptance criteria AC1..AC14

- AC1: Given valid Atlassian credentials in the request headers and a JQL query, When the agent calls `atlassian_jira_search_issues`, Then matching issues are returned (key, summary, status, assignee, updated) up to the requested limit (default 25, hard cap 100), and an empty result set is returned as an empty list, not an error.
- AC2: Given a valid issue key, When the agent calls `atlassian_jira_get_issue`, Then the issue's key/summary/status/assignee/description/comments-count are returned; Given a non-existent issue key, Then a structured `not_found` error is returned (no 500, no stack trace).
- AC3: Given a project key, summary, issue type, and description, When the agent calls `atlassian_jira_create_issue`, Then the issue is created in Jira and its key and web URL are returned; Given a non-existent project key, Then a structured `invalid_argument` error is returned.
- AC4: Given an issue key and one or more fields to change (summary, description, assignee), When the agent calls `atlassian_jira_update_issue`, Then only the supplied fields are changed on the issue; Given an unsupported field name, Then a structured `invalid_argument` error names the rejected field.
- AC5: Given an issue key and a target status name, When the agent calls `atlassian_jira_transition_issue`, Then the issue moves to that status if the transition is valid from its current status; Given a status that is not a valid transition from the current state, Then a structured error lists the transitions that are actually available.
- AC6: Given an issue key and comment text, When the agent calls `atlassian_jira_add_comment`, Then the comment appears on the issue and its comment id is returned.
- AC7: When the agent calls `atlassian_jira_list_projects` with no filter, Then every project visible to the supplied credentials is listed (key, name, project type).
- AC8: Given a CQL query, When the agent calls `atlassian_confluence_search_pages`, Then matching pages are returned (id, title, space key, web URL) up to the requested limit, and no matches returns an empty list, not an error.
- AC9: Given a page id, When the agent calls `atlassian_confluence_get_page`, Then the page's title, space, body (plain-text extract), and version number are returned; Given a non-existent page id, Then a structured `not_found` error is returned.
- AC10: Given a space key, title, and body, When the agent calls `atlassian_confluence_create_page`, Then the page is created and its id and web URL are returned; Given a title that already exists in that space under the same parent, Then a structured `invalid_argument` error is returned (Confluence's own 400 on duplicate title is mapped, not passed through as a 500).
- AC11: Given a page id, new body, and the page's current version number, When the agent calls `atlassian_confluence_update_page`, Then the page content is updated and the version increments by one; Given a stale version number (someone else edited the page first), Then a structured error reports the conflict instead of silently overwriting.
- AC12: When the agent calls `atlassian_confluence_list_spaces` with no filter, Then every space visible to the supplied credentials is listed (key, name).
- AC13: Given a request that is missing one or more required credential headers, When any tool is called, Then the service returns HTTP 401 listing the missing headers, and no outbound call is made to Atlassian.
- AC14: Given two concurrent requests that carry different tenants' credentials (different `X-Atlassian-Site` values), When both call any tool at the same time, Then neither response contains data belonging to the other tenant's site, and this holds under concurrent load (no module-level or global state caches one request's credentials or response for reuse by another).

## Tech design

### Conclusion

Build `atlassian-mcp` from scratch (SOP main line A: new vendor, no existing tools to extend) as a Python 3.12 + `uv` + FastMCP Streamable-HTTP service, following the same shape every other vendor MCP in `MSPbotsAIFramework` uses. Two REST clients (Jira Platform REST v3, Confluence REST v2) share one Basic-auth credential set read per-request from Headers; twelve tools wrap the handful of Jira/Confluence endpoints needed for the v1 scope in § Goals. No new infrastructure, no gateway change, no OAuth flow — this is a self-contained vendor service like the ~45 others already registered.

Nothing exists yet. `https://github.com/MSPbotsAIFramework/atlassian-mcp@main` (4348cb8) is the empty scaffold (`README.md` only — see § Current state). There is no prior Jira/Confluence integration anywhere in `MSPbotsAIFramework` to extend or diff against (confirmed by the vendor's own repo search in ClickUp comment 1793374126741, and re-confirmed here).

### Option analysis

**Auth mechanism** (the one real fork in the road for this design):

| Option | How | Pros | Cost | Verdict |
|---|---|---|---|---|
| API token + Basic auth | `Authorization: Basic base64(email:api_token)` against `https://<site>.atlassian.net/...`; token from `id.atlassian.com/manage-profile/security/api-tokens`, long-lived until revoked | Matches the "credentials only in Header, no server-side state" MCP contract exactly; matches `vendor-register`'s `credential_fields` model (plain headers, no OAuth support per `mcp-track.md` §2.2/`SKILL.md` "a new vendor needing OAuth is not supported by the registration API"); no token-refresh machinery needed in a stateless service | Per-user API tokens, not scoped OAuth grants; Atlassian's long-term direction favors OAuth for new apps | **Chosen for v1** |
| OAuth 2.0 (3LO) | Authorization-code grant, `access_token` + `refresh_token`, calls go through `api.atlassian.com/ex/jira/{cloudId}/...` | Finer-grained scopes, user-attributable actions | Requires a consent UI, a token store, and refresh-before-expiry logic — none of which this stateless, per-request-credential service is built to hold; the `vendor-register` API that onboards a new vendor explicitly does not support OAuth vendors (manual registration only) | Rejected for v1; candidate for a follow-up once there is a credential-vaulting story on the gateway side |

**Jira search endpoint**: use `POST /rest/api/3/search/jql` (the "enhanced" search, cursor/`nextPageToken`-based), not `GET/POST /rest/api/3/search` — the latter is marked Deprecated on Atlassian's own docs (verified 2026-11-02). No other option considered; building against a documented-deprecated endpoint would ship already-obsolete code.

**API library**: no fork/mirror of any third-party Atlassian SDK or open-source `atlassian-mcp` — SOP rule 3 (`vendor-mcp-development/SKILL.md` §"open-source repos are reference only") requires a clean-room build against the vendor's own docs. Reuse is `httpx` (async HTTP client) + `FastMCP`, the same stack every sibling MCP in this org uses; no Atlassian-specific open-source client is pulled in.

### Decisions made by DEV01

No one was available to answer these; each is a reversible, in-repo choice, not a platform-level commitment:

1. **Auth: API token + Basic auth, not OAuth 2.0 (3LO).** Why: matches the Header-only, stateless credential contract and the `vendor-register` API's plain-credential model (see Option analysis). Alternative not chosen: OAuth 3LO — needs consent flow + token storage this service isn't built to hold.
2. **Tenant site identification: `X-Atlassian-Site` carries the full Cloud base URL** (e.g. `https://acme.atlassian.net`), used directly as the REST API host. Alternative not chosen: resolving a `cloudId` via `api.atlassian.com/oauth/token/accessible-resources` — that lookup only works with an OAuth bearer token, which v1 does not use.
3. **API versions: Jira Platform REST v3, Confluence REST v2.** Alternative not chosen: Confluence REST v1 — v2 is Atlassian's current recommended API; several v1 endpoints are already flagged legacy on Atlassian's own docs.
4. **Jira search: `POST /rest/api/3/search/jql`, not the deprecated `/rest/api/3/search`.** See Option analysis.
5. **Tool scope v1 = 12 tools** (§ Goals). Alternative not chosen: also shipping boards/sprints (Jira Software Agile API) or attachments in v1 — would roughly double the surface and this ticket named no specific need for either; kept as explicit non-goals for a follow-up.
6. **Pagination: cursor-based, default `limit` 25, hard cap 100** (`nextPageToken` for Jira enhanced search, `cursor` for Confluence v2), consistent with the SOP's "≤200 hard ceiling, never unlimited" tool-design rule. Alternative not chosen: offset/`startAt` paging — Atlassian is moving its newer endpoints away from offset paging.
7. **Write tools take explicit resource ids only** (issue key, page id + version) — no title-based fuzzy lookup-and-write. Matches the SOP's "write/delete tools accept only unambiguous resource ids, no fuzzy batch" rule.

### Data & API contract

All 12 tools share the three credential headers (never logged, never echoed back in responses):

| Header | Required | Meaning |
|---|---|---|
| `X-Atlassian-Site` | yes | Cloud site base URL, e.g. `https://acme.atlassian.net` (no trailing slash) |
| `X-Atlassian-Email` | yes | Account email used for Basic auth |
| `X-Atlassian-Api-Token` | yes | API token from `id.atlassian.com/manage-profile/security/api-tokens` |

Missing any of the three → `401`, body `{"error": {"code": "unauthorized", "message": "missing required headers: X-Atlassian-Site, X-Atlassian-Api-Token", "retryable": false}}`.

Error envelope (all tool-level failures, never a raw exception/stack trace):
```
{"error": {"code": "<not_configured|unauthorized|not_found|invalid_argument|rate_limited|upstream_error>", "message": "<human string>", "retryable": <bool>}}
```

Representative tools (full request/response shape; the remaining 10 follow the same pattern against the Jira/Confluence endpoint named in the table below):

**`atlassian_jira_search_issues(jql: str, limit: int = 25, fields: list[str] | None = None)`**
→ `POST {site}/rest/api/3/search/jql` with `{"jql": jql, "maxResults": min(limit, 100), "fields": fields or ["summary","status","assignee","updated"]}`
→ returns `{"issues": [{"key": "ABC-1", "summary": "...", "status": "In Progress", "assignee": "jane@acme.com", "updated": "2026-11-01T12:00:00Z"}], "next_page_token": "..." | null}`
→ errors: bad JQL → `invalid_argument`; 401/403 from Atlassian → `unauthorized`; 429 → `rate_limited` (honors `Retry-After`).

**`atlassian_confluence_create_page(space_key: str, title: str, body_html: str, parent_id: str | None = None)`**
→ `POST {site}/wiki/api/v2/pages` with `{"spaceId": <resolved from space_key>, "status": "current", "title": title, "parentId": parent_id, "body": {"representation": "storage", "value": body_html}}`
→ returns `{"id": "123456", "title": "...", "url": "{site}/wiki/spaces/{space_key}/pages/123456"}`
→ errors: duplicate title in space/parent (Confluence 400) → `invalid_argument` with the duplicate-title message; space not found → `not_found`.

| Tool | Endpoint | Method | Key params | Returns |
|---|---|---|---|---|
| `atlassian_jira_search_issues` | `/rest/api/3/search/jql` | POST | `jql`, `limit`, `fields` | issues list, `next_page_token` |
| `atlassian_jira_get_issue` | `/rest/api/3/issue/{key}` | GET | `issue_key` | key/summary/status/assignee/description/comment_count |
| `atlassian_jira_create_issue` | `/rest/api/3/issue` | POST | `project_key`, `summary`, `issue_type`, `description` | key, url |
| `atlassian_jira_update_issue` | `/rest/api/3/issue/{key}` | PUT | `issue_key`, `fields` (partial) | `{"updated": true}` |
| `atlassian_jira_transition_issue` | `/rest/api/3/issue/{key}/transitions` | GET then POST | `issue_key`, `target_status` | `{"transitioned_to": "..."}` or error listing available transitions |
| `atlassian_jira_add_comment` | `/rest/api/3/issue/{key}/comment` | POST | `issue_key`, `body` | `{"comment_id": "..."}` |
| `atlassian_jira_list_projects` | `/rest/api/3/project/search` | GET | `limit` | projects list (key, name, type) |
| `atlassian_confluence_search_pages` | `/wiki/api/v2/pages` with `cql`-equivalent `title`/`space-id` filters, or `/wiki/rest/api/search` (CQL) | GET | `cql`, `limit` | pages list (id, title, space_key, url) |
| `atlassian_confluence_get_page` | `/wiki/api/v2/pages/{id}?body-format=storage` | GET | `page_id` | title, space, body (plain-text extract), version |
| `atlassian_confluence_create_page` | `/wiki/api/v2/pages` | POST | `space_key`, `title`, `body_html`, `parent_id` | id, url |
| `atlassian_confluence_update_page` | `/wiki/api/v2/pages/{id}` | PUT | `page_id`, `body_html`, `current_version` | `{"version": N+1}` or conflict error |
| `atlassian_confluence_list_spaces` | `/wiki/api/v2/spaces` | GET | `limit` | spaces list (key, name) |

**Backward compatibility**: this is a new vendor, so there is no existing `tools/list` contract to preserve. Any change after the first version lands follows SOP §13 (breaking vs. compatible) and updates `tests/test_tools.py`'s snapshot.

### Key flow / sequence

```
Agent (Claude/ChatGPT/Cursor/etc.)
  -> MCP Gateway (mcp-service-gateway, read-only reference @main)
    -> atlassian-mcp /mcp  (Headers: X-Atlassian-Site/Email/Api-Token)
      -> middleware: validate headers present -> set ContextVar -> else 401
      -> tool fn: build request via jira_client/confluence_client
        -> httpx -> https://{site}.atlassian.net/rest/api/3/... (or /wiki/api/v2/...)
        <- Atlassian REST response
      <- map status -> success payload | structured error envelope
    <- finally: ContextVar.reset()
  <- tool result (JSON string, compact, ensure_ascii=False)
```

### Non-functional

- **Idempotency & concurrency**: reads are naturally idempotent. `atlassian_jira_update_issue`/`atlassian_confluence_update_page` are not retried blindly by this service (a retried PUT could double-apply a version bump on Confluence) — callers get the structured error and decide; Confluence's optimistic-lock version number (AC11) is the concurrency guard on that one genuinely conflict-prone path. No local state is shared across requests (SOP §3.3), so concurrent calls from different tenants cannot interleave state.
- **Performance**: 5s connect / 30s read timeout per outbound call; retry with backoff on 429/5xx honoring `Retry-After`, total time per tool call capped under 120s (SOP §5); list/search tools default `limit=25`, hard cap 100 (no unlimited fetch); responses serialized compact (`ensure_ascii=False`, no `indent=2`) and only the fields named in § Data & API contract — full raw Atlassian payloads are never echoed back.
- **Security**: credentials exist only for the lifetime of one request's `ContextVar`; never written to disk, env, or logs; outbound calls are TLS-only to the tenant's own `*.atlassian.net` host taken from `X-Atlassian-Site` (no server-side allowlist needed beyond "must be https"); error messages from Atlassian are passed through for diagnosability but credential values are never included in them.
- **Multi-tenant isolation**: the credential set (site + email + token) *is* the tenant boundary — every outbound call is scoped to the site named in that request's headers, there is no shared Jira/Confluence "account" the service holds on anyone's behalf, and no cache keys on anything less specific than the full credential tuple (there is no cache at all in v1 — see Risks).
- **Observability**: structured log per tool call — request id, tool name, Atlassian endpoint + HTTP status, latency; never logs header values, JQL/CQL query text verbatim (may contain tenant data), or issue/page bodies. `/health` is a local liveness probe only (SOP §1.1), independent of Atlassian's own uptime.

### Rollout & rollback

- First version: push directly to `main` (no `dev-lock` needed for a repo nobody else is touching yet, per SOP §A2), then register via `/api/vendor-register` (new vendor, not yet known to the INT gateway) — this both deploys and onboards the vendor in one step.
- No feature flag needed (brand-new vendor; nothing to gate for existing tenants since there are none yet for this connector).
- Rollback: revert the merge commit on `main` and re-run `/api/deploy-int` — there is no data migration or schema to roll back (this service holds no persistent state of its own).
- Release order: single repo, no cross-repo dependency — `release order: any` is moot here (only one repo is touched), no platform-side change is required.

### Test strategy

- **Unit (auto, mocked HTTP via `respx`, no real Atlassian account needed)**: one test per tool verifying (a) the outbound request is built correctly from the tool's parameters, and (b) each documented error case maps to the right structured error code. Plus the `tools/list` snapshot (12 tools) and the two middleware tests (missing-header 401, concurrent-request isolation).
- **Manual (needs a real Atlassian Cloud site + API token — not available to this design; flagged, not a blocker per SOP "no test account still publishes to INT as usual")**: live round-trips for search, get-on-missing-key, create, and a valid transition, confirmed against a real site rather than a mock.
- **Regression face**: none — this is a new, isolated service; no existing tool or tenant can regress from this ticket.

### Effort & breakdown

Story points: 3
Tier: cross-service flow, security/multi-tenant isolation, many acceptance scenarios (row "3")
Considerations: 1 new repo/service (not a modification); 2 external REST surfaces integrated (Jira + Confluence) behind one credential set; external API is well-documented (public, verified reachable) but entirely unknown to this codebase — no prior Atlassian integration to copy; write operations exist (create/update/transition/comment, no destructive deletes); no data migration; multi-tenant credential isolation is a first-class, must-not-fail requirement (SOP's three "iron laws"); no UI; 14 acceptance scenarios across 12 tools
Main uncertainty: exact Confluence v2 "duplicate title" error shape (400 body format) and exact Jira `search/jql` cursor semantics — both documented but not yet exercised against a live site; resolved during dev leg's implementation against the public docs, or confirmed once a real test account is available
Order inside this ticket: 1) scaffold + middleware + error envelope + health check, 2) Jira client + 7 Jira tools, 3) Confluence client + 5 Confluence tools, 4) README (headers table + Connector section), 5) `vendor-register`

### Risks & dependencies

- **No test account available at design time**: per SOP, this does not block shipping — the dev leg ships with unit tests against mocked responses and marks the 5 manual cases "needs a real vendor account"; INT registration still proceeds.
- **Atlassian rate limits**: Jira/Confluence Cloud enforce per-app rate limits; the 429/backoff handling in § Non-functional is the mitigation, no further dependency.
- **Confluence v1 vs v2 API drift**: v2 is current but some capability (e.g. certain search filters) is still only exposed via the older `/wiki/rest/api/search` CQL endpoint (noted in the contract table for `atlassian_confluence_search_pages`) — dev leg confirms which concrete endpoint covers the AC8 cases during implementation; this is an implementation detail, not a product-visible risk.
- **No dependency on any other ClickUp ticket or MSPbots repo** — this is a self-contained new vendor with no platform-side change required.
- **Future OAuth 2.0 request** (see Decisions #1): if the requester later wants per-user-attributed OAuth access, that is new scope, not a defect in this design.
